## 2. 通用请求误变为对象约束的完整来源链

链条为：**适配器固定 query → 基础 TASK 提示 → 原模型 JSON → validate_task → 保存的 TaskSpec → 400 份比较输入**。

| 环节 | 实际证据 | 可以得出的结论 |
|---|---|---|
| 输入 | `tvsum_adapter.py` 的 QUERY 与十条冻结输入均为 `Highlight of this video.` | 没有具体画面对象、数量或时长要求 |
| 调用入口 | 冻结 `core.py::one_video` 使用 `TASK`、`TaskSpec`、`validate_task` | 本轮没有调用 `task_grounding.extract_task`；不能以该模块存在推断它已生效 |
| 原响应 | 十次 `/task` 原始响应均含 `request_type=generic` 与 `object` 约束 `Highlight of this video` | 该错误字段来自模型提取，不是适配器在结果之后写入 |
| 校验 | `schema.py::validate_task` 检查 quote 非空且是 query 子串，检查数字字段 | 引用可追溯不等于语义上真是对象约束；这个伪约束会通过 |
| 下游 | 全部 400 份比较原始输入包含与记录一致的 TaskSpec | 不能解释为“文件中保存错了，但模型没看到” |

原约束和删除后的空约束均通过冻结基础校验器。这里的“错误”是通用请求与方法定义中的对象约束不匹配，不是根据高光标签判定。也没有证明改用现成的 grounded 提取入口就能解决它；下一轮因此只改这个中间字段，不同时替换提取提示或 schema。

**P_pair 不使用该 TaskSpec。** 它在任务解析之前直接读取原 query 与帧，所以不能用这一错误解释其 −2.94 pp，也不能宣称本单变量协议会修复 P_pair。

每条来源链有视频 ID、原始调用相对路径、响应 SHA-256、旧/新 TaskSpec 和变化字段。冻结源函数的行号与哈希另记于 `fact_lineage.json::source_locations`。

## 3. 资格、并列和证据不足：已知到哪一步

原直接比较的 400 个单侧资格均为 unknown；带记忆后有 88 个 satisfied、312 个 unknown，但两组都没有 a_better/b_better。原 28/100 个记忆组资格换位不一致继续保留。新审计逐对连接两个条件，得到：

| C_direct4 → E_memory（有向比较） | 数量 |
|---|---:|
| tie → tie | 178 |
| tie → insufficient | 12 |
| insufficient → tie | 5 |
| insufficient → insufficient | 5 |
| 合计 | **200** |

记忆使 12 对变得证据不足、5 对从证据不足变成并列，仍没有形成胜负；这比单看两个条件总体 tie 比例更能说明变化的位置。

另做 **80 个合成 CPU 契约例**：十视频×两条件×四种 preference，沿用各自合法双侧引用，固定资格 unknown。四态都能通过冻结后置校验；输出 schema 也允许资格 unknown 的一方获胜。排名函数根据双向 preference 建边，不读取 TaskSpec。

因此已排除“后置校验器要求 satisfied 才能获胜，机械地把 unknown 全变成 tie”的解释。**这不是实际模型预测，也不是 tokenizer/语法解码可达性测试**，不能据此排除全部解码或模型偏好问题。错误对象约束是否诱导 unknown、tie 或无效比较，仍是待检验因果关系。

## 4. 记忆丢失发生在哪个环节

新审计将 448 条记录逐项连接到 **50 次原始事实提取**，核验帧 ID、PTS、候选像素指纹和 query-free 提示；再连接记忆生成草稿与容量处理后的活动视图。未重新调用事实提取器、压缩器或 tokenizer。

| 阶段 | 全部事实记录 | 其中 unknown |
|---|---:|---:|
| 原事实库 | 448 | 185 |
| 模型记忆草稿引用 | 143 | 16 |
| 活动记忆最终保留 | 130 | 9 |
| 草稿阶段未选中 | **305** | **169** |
| 草稿已选中、容量阶段再移除 | **13** | **7** |

上述“事实记录”包含 unknown，不能全部称为已观察到的事实。移除环节按 ID 集合与原 `capacity_evictions` 精确核对：305＋13＋130＝448，169＋7＋9＝185。容量驱逐只出现在 `sTEELN-vY30`（6 条）和 `Yi4Ij2NM7U4`（7 条），其它八条为 0。

**主要记录损失发生在记忆草稿选择阶段。** 不能再将这些损失主要归因于 1,024-token 后处理；同时也不能断言提高容量或取消 12 项草稿限制必然无效，因为模型选择和输出项数可能相互影响。本轮只定位环节，不修改记忆来验证收益。

## 5. 可疑事实与引用问题的传播证据

沿用前轮助手对自行车视频 `JgHubY5Vw3Y` 候选 53 的抽查：输入被判断为车锁/钥匙操作，事实 `c53_f0`、`c53_f4` 却描述后拨调整和链条运动。该视觉判断是**已有共享上下文助手案例，不是本轮新增人工标注或独立真值**。

新追踪确认两条描述在原事实响应、记忆草稿、活动视图中都有对应内容，随后：

- `c53_f0` 被 **7 条**记忆比较在结构化证据或理由中引用。
- `c53_f4` 被 **6 条**记忆比较引用；两组有重叠，不能相加当作 13 条不同比较。
- 这些比较全部为 tie。可以确认可疑证据进入了理由链，不能说它已导致排序下降或改变了高光指标。

两条明确的理由归属错配也保留原始文字和结构化引用：自行车 **53→51** 的理由把 B 写成 `c52_f0/c52_f3`，结构化 B 引用却是 `c51_f0/c51_f3`；舞蹈 **12→19** 的理由把 B 写成 `c18_f3/c18_f1`，结构化 B 引用属于 19。前后来源可追踪，说明字段级引用检查没有涵盖自由文本归属。

对全部比较的额外静态扫描发现：

- **19 条** E_memory 理由显式提到当前 A/B 之外的事实 ID，跨七视频；这仅是复核标记，其他候选作为上下文不必然错误，不能把 19 条都计成归属错误。
- **48 个** E_memory 单侧引用列表有重复 ID；这是 400 个单侧列表中的计数，不是 48 个视频或 48 次技术失败。原契约允许重复，重复项不能算独立证据。

本轮不自动改写理由、去重输入、删除可疑事实或放宽引用规则。下一轮仍固定原记忆，使对象约束成为唯一变量。

## 6. 证据等级与当前结论

| 命题 | 等级与边界 |
|---|---|
| 基础校验接受伪对象约束，且它进入全部比较输入 | **已复现的契约问题**：十条来源链与 400 份请求逐项核对 |
| 305 条记录未进入草稿，13 条因容量再丢失 | **已复现的处理路径事实**：原响应/ID 集合/容量记录一致；不等于这些遗漏都损害精度 |
| 后置校验不要求 unknown 一律并列 | **已复现的 CPU 契约行为**：不能当成模型或实际解码行为 |
| 两条理由把 B 归给别的候选 | **已复现的文本/结构化归属不一致**：不依赖高光 GT |
| 车锁被描述为后拨/链条，并被记忆传播 | **有既有助手案例支持**：传播链已核验，视觉真值未独立确认 |
| 错误约束导致全部 tie，或删掉它即可提高 mAP | **待检验**：本轮没有任何新模型输出 |
| 记忆 unknown 丢失导致 88 个 satisfied | **待检验**：二者共现，未隔离因果 |

当前最小下一步仍是仅删除错误对象约束的对照，不能先给它记一项“已验证的修复收益”。
