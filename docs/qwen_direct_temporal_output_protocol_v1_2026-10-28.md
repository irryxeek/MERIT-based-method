## 1. 问题与唯一干预

研究问题：**在相同视频输入与任务下，将按位置排列的分数改为带明确起止秒数的分数，是否缓解当前视频内部全部同分的现象？**

唯一实验因素是输出表示 `positional_array → interval_keyed_object`。控制组为冻结的原 Direct QV20，零新增控制组调用；候选条件仍是整视频一次判断，不增加价值分类、记忆、比较、回看、采样或分段调用。

```json
{"scores": [80, 80]}
```

改为：

```json
{"scores": {"0-2": 80, "2-4": 80}}
```

上面是两格格式示意，不是模型预测，也不作为示例分数发送给模型。键 `s-e` 表示秒区间 `[s,e)`；正式输入覆盖全部 64 或 75 格。**整段同分始终合法，不要求制造分差或胜负。**

这是可以解释的“输出表示”对照，不能单独证明时间语义的因果作用：时间键、键值语法、生成位置和序列长度不可避免地共同变化。若结果改善，只能说该表示方案在此固定开发集上有效；要分离时间语义与格式长度，需要另立匹配长度的对照，本轮不扩展。

保留原 QV20 **全部样本及原执行顺序**：


不按指标或案例类型重新筛选。`5172` 为 64 格，其余 19 条为 75 格；格数继续为 `floor(duration/2)`，尾部不足 2 秒不新增格。

固定内容包括：原 query、视频、持续时间、同一 64 帧 `.npy` 像素及顺序、真实 PTS/源帧索引、缩放尺寸、视频元数据、Qwen 原生时间合并和视觉网格。不开原视频重新解码，也不重抽帧。

模型仍为本地 Qwen3-VL-8B-Instruct BF16，revision `0c351dd01ed87e9c1b53cbc748cba10e6187ff3b`。SYSTEM、temperature=0、top_p=1、top_k=-1、seed=0、输出上限 2,048、上下文 8,192、原引擎配置全部沿用。模型权重验证复用旧凭证；本轮只读取 tokenizer/配置，不读取权重。未来启动前仍须核验模型版本与文件凭证，漂移则停止。

未来建议与原 QV20 一样从新进程冷启动，单 worker 按上述顺序处理 20 条后退出；不连接旧服务、不夹入 TVSum，也不增加缓存/调度器改动。旧 QV20 已成功仅支持运行可行性，不保证新运行不会 OOM；故障时按第 7 节停止。

## 3. 提示、schema 与导出契约

原提示从任务开始到评分定义完全逐字保留，包括 query、64 帧的时间说明、每 2 秒的区间定义，以及 0–100 分含义。仅替换最后的输出格式说明。完整逐样本提示和变更段已保存在 `prepared_inputs.json`、`prompt_diffs.json`。

新格式段模板为：

```text
Return only a JSON object with a single key "scores" containing an object with exactly {N} entries. Use each interval's start and end times in seconds as its key: "0-2", "2-4", ..., "{last_start}-{last_end}". Each key denotes [start,end), and its value is that interval's integer score. Include every interval exactly once, in increasing time order. Do not include explanations or additional keys.
```

模板中的占位符在每条正式准备输入中已替换为真实整数，其中 `last_start=2N-2`、`last_end=2N`；例如 75 格的最后键是 `148-150`，不会把模板公式送给模型。

schema 规定唯一顶层字段 `scores`，其对象键是完整的 `0-2,2-4,…`，全部 required，禁止额外键；值只能为整数 0–100。沿用原 xgrammar 紧凑 EBNF 生成方式、无额外空白，并固定按时间顺序生成。

CPU 导出器只做**按既定键取值、恢复原长度评分向量**。拒绝重复/缺失/额外/错序/偏移键、布尔值、浮点数、越界值、截断 JSON；不重排修补、不填零、不插值、不回退到控制组，不改变数值。时间键是预先确定的元数据，不能视为模型预测的边界。

最终主评价继续使用原完整 2 秒向量；辅助区间仍固定 `score >= 50` 后合并相邻格，不限制高光数量和时长。两种表示导出同一向量时，评价与辅助区间必须完全相同。

## 5. 新增 CPU 检查与不可避免的成本差异

本轮未重跑旧 OOM 模拟、常数输出审计或失败分类。

- **20/20** 原多模态 prompt token 序列哈希精确重现，并匹配实际成功请求长度。重现只使用冻结元数据、网格和 tokenizer，未计算视觉 embedding、未加载权重。
- 新提示每条比旧提示多 **64 token**；新输入范围 **4,633–5,153 token**。
- 保留每条 2,048 输出预留，最大上下文占用 **7,201/8,192**，最小余量 **991 token**；全 20 条总预留 **143,289 token**。
- 64/75 格紧凑输出的保守规范序列字节界（含一个终止 token）分别 **801/955**，低于原输出上限。另以实际 tokenizer 检查合法等分和变分值样例。
- 7 项导出/格式单元测试、14 个新 schema 语法案例、4 条实际 Qwen 词表 token-mask 路径通过，等分与变分值均可接受。CPU 合成数组不是模型预测。

同样一组值，输出中必须多生成时间键。例如 75 格全 80 的规范输出从 **228** 增至 **720 token**，全 100 从 **303** 增至 **795 token**（均不含终止 token）。这是语法开销，不是新证据或新增决策。实际总输出 token、推理时间未来必须单独报告，不能宣称成本相同。

本轮验证是 CPU 可表达性与上下文检查，**未证明新条件能产生非恒定评分，也未验证运行时 GPU 输出/显存行为**。

## 6. 后续结果判定与全分母规则

固定统计单位为 20 条 query；本轮沿用开发集，不能当成未见测试集或独立泛化验证。

1. 先报告每条完成状态、常数/非恒定分数、不同分值数和最大分值并列数量；全等分是合法负结果，不因其出现而改提示、重试或挑样本。
2. 完整 20/20 有效且来源校验通过后，复用官方 QV VeryGood mAP、Hit@1，逐 query 配对冻结 Direct 控制组（10.7111/15.00），并保留全部差值。旧 REZE 只能列为历史参照，不承担单变量控制组角色。
3. 任一技术失败或未调用，都保留在 20 条分母中，不能用旧分数回退。完整集新主指标记为“未完成”；可另列有效样本与**相同 ID**旧控制的部分诊断，但不能替代全 20 结果。
4. 非恒定输出增加不等于精度提高。若仍为 20/20 常数，输出表示假设未获支持；若仅少数有分差，只报告其数量及配对指标。不能宣称恢复了时间理解，更不能直接归功于回看/价值判断。
5. 进入下一阶段案例审阅的门槛为：20/20 有效、至少一条非恒定、mAP 高于冻结 Direct、Hit@1 不低于冻结 Direct；使用原评价文件的未舍入值判定。这只是预先固定的探索性门槛，不是显著性或泛化结论。无论是否通过，本协议都不自动启动 Agent 模块或扩样。
